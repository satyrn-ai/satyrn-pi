# P2.1 contributor setup: design

## Reviewer brief

**Intent:** a new contributor clones the repository, reads the README, runs one
setup command, and opens Pi with the Superpowers skills at a recorded revision.

**Decisions:** `npm run setup` runs the locked installs and pins Superpowers
(`bb92a77`, `v7.0.0`); an existing different or unpinned entry is refused
without `--yes`; the revision record carries the upgrade policy; the proof uses
a scratch `PI_CODING_AGENT_DIR`.

**Non-goals:** root `AGENTS.md`, wrapper skill, backlog and pathologies (P2.2);
executable gates (P2.3–P2.5); the discovery demonstration (P2.6); runtime code;
the end-user installer walkthrough (P9.1).

**Verification:** fresh-clone setup, both default suites, `pi list` and the
checkout at the pin, idempotence and refusal, preserved files untouched.

Phase 2 is split into six stacked cycles (P2.1–P2.6), one branch and one PR
each. This document covers **P2.1 only**: a new contributor clones the
repository, reads the README, runs one setup command, and opens Pi with the
Superpowers skills available at a recorded revision.

## Intent and why

Superpowers is the contributor development workflow for this port, but nothing
in the repository today makes it available to a new contributor's Pi, and no
revision is recorded. P1.1 excluded the staging README, so the repository has
no entry point either. P2.1 supplies both, so that P2.2's root `AGENTS.md` and
rules index can assume a working, reproducible setup instead of describing one.

The subject Mellum worker is unaffected: these are contributor skills, and the
worker loads none of them by default.

## Goals

- A short contributor-facing `README.md`: what the project is, prerequisites,
  clone → `npm run setup` → open Pi, the default test commands, and where the
  governing rules and documents live.
- `scripts/setup.mjs`, exposed as `npm run setup`, which on a fresh clone:
  1. checks `uv` and `pi` are on PATH, failing early with clear errors;
  2. runs `npm ci` and `uv sync` (locked dependency installs);
  3. installs Superpowers into the contributor's Pi as a ref-pinned git
     package: `pi install git:github.com/obra/superpowers@bb92a77741419a4ab5f06e711a283343f1ada0c3`;
  4. prints each step as it runs and a summary of what changed and what to do
     next.
- A written revision and setup record at `docs/superpowers/setup.md`: the
  pinned commit, its `v7.0.0` description, how the skills become
  visible to Pi, the side effects of setup, and the upgrade policy below.
- Fresh-clone proof as PR evidence: the commands run and their observed
  result, including the skills being visible to Pi afterwards.
- Roadmap rows for P2.2–P2.6 and a `## Now` update, so the split is recorded
  in the same PR that starts it.

## Non-goals

- Root `AGENTS.md`, the local wrapper skill, `BACKLOG.md`,
  `docs/pathologies.md` (P2.2).
- Executable gates: caps/lifecycle/evidence (P2.3), vocabulary (P2.4),
  tripwire and import direction (P2.5).
- The new-contributor discovery demonstration and phase close (P2.6).
- Any runtime code, worker behaviour, eval execution, or measurement claims.
- The end-user installer walkthrough (P9.1); publishing either package.

## Anti-goals

- Vendoring or copying Superpowers into this repository.
- A floating `main`/`latest` reference, or a background refresh of the pin.
- Silently changing a contributor's existing Pi configuration (see below).
- Running the setup script, a subprocess, or the network in the default test
  suites; both suites stay model-, network- and subprocess-free.
- Editing the preserved source documents (`docs/sdd.md`,
  `docs/provenance/`).

## Constraints

- Stacked on `p1.2/vocabulary` (`015c93d`), which is in review and unmerged;
  the branch is `p2.1/contributor-setup` in the existing worktree. Later
  cycles stack on this branch.
- Node >= 20, npm package `satyrn-pi` 0.1.0, Pi peer range `^1.1.0`
  (targeting 1.5.2); Python always through `uv run`.
- Documents are plain Markdown that render on GitHub without a generator;
  document caps and plan front matter from `docs/sdd.md` apply at every edit.
- Pi pins git tags and commits: `pi install git:…@<commit>` reconciles the
  checkout to that ref and does not move it on later updates.
- One PR for Nicola; the changelog gets an `[Unreleased]` line for the
  contributor-facing additions.

## Decisions

- **Single command.** `npm run setup` also runs `npm ci` and `uv sync`, so the
  README flow is one command. npm scripts work without `node_modules`, and CI
  keeps calling `npm ci`, `uv sync` and the test commands directly. (Paul's
  decision, confirmed in brainstorming.)
- **Pinned revision.** Exact commit `bb92a77741419a4ab5f06e711a283343f1ada0c3`
  (v7.0.0, 2026-10-09) — the revision that actually drove P1.1 and
  P1.2. (Assistant's call, stated in brainstorming and not rejected.)
- **Existing-install protection.** Setup inspects the contributor's Pi
  configuration first. No Superpowers entry: install at the pin. Same ref:
  no-op, reported as already configured. A different ref or an unpinned entry:
  report the current and requested refs and require an explicit opt-in flag to
  change it; never silently rewrite a rig that other projects use. (Assistant's
  call: the package is user-level, shared across projects.)
- **Upgrade policy.** Adopting another Superpowers revision is a named decision
  recording the new commit, the skills and contracts affected, and the evidence
  limits; it is reviewed like any other cycle and never inferred from fetching
  newer code.
- **Honesty about proof.** The setup script is exercised manually on a fresh
  clone and the outcome is recorded in the PR and the plan's result; no default
  test shells out to it. Model-free tests may assert static facts (the npm
  script wiring, the pin's shape) if that stays cheap.

## Left to the builder

- Exact script structure and output wording; how it reads Pi's configuration;
  the opt-in flag's name; whether `pi install` needs any non-interactive flag.
- README section layout and length, keeping it short and contributor-focused.
- Whether the static model-free tests are worth adding, decided test-first.
- How the fresh-clone proof is produced (temporary clone or worktree) and how
  much of its transcript belongs in the PR versus the plan record.

## Verification

- Fresh clone → `npm run setup` → `npm test` and `uv run pytest` pass → Pi
  started in the clone shows the Superpowers skills.
- Re-running `npm run setup` is a reported no-op for the Superpowers step.
- A rig with a different Superpowers ref is not changed without the opt-in.
- `git diff --check`, document caps respected, no changes under
  `docs/provenance/` or to `docs/sdd.md`.
