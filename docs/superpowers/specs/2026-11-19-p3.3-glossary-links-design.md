# P3.3 glossary links: design

## Reviewer brief

**Intent:** a reader on the site meets a defined term and can open its
definition from the sentence that uses it.

**Decisions:** configure `zensical_glossary` with `glossary_file` resolving to
`docs/glossary.md`, `heading_level = 3`, `first_only = true` and a `base_url`
equal to the deployed glossary page; review every alias against the vocabulary
decisions and remove the misleading ones; verify first-occurrence links,
tooltips and the three exclusions by building and reading the rendered pages;
prove the refusal case with a term inside a code span.

**Non-goals:** new glossary entries, a repository-wide terminology sweep,
hand-linked prose, a second glossary source, or an automated check that runs
the build inside the default suite.

**Verification:** a defined term appears as a link at its first prose use on
each page and only there; the same term inside a code span and inside a heading
stays plain text; an existing link is not wrapped twice; the alias review is
recorded; the list of terms that actually fired is reviewed on both pages.

## Intent and why

The glossary is the only content the site carries besides the home page, and
`docs/glossary.md` already marks its aliases in HTML comments. Until this cycle
they do nothing: a visitor reading "remedy" gets a plain word. Linking the first
use of each term is the smallest thing that makes the page useful, and it is
deliberately last because its `base_url` is the deployed path, which only
exists after P3.2.

## Goals and non-goals

- `project.markdown_extensions.zensical_glossary` configured with
  `glossary_file = "glossary.md"` (resolving under `docs_dir`), `heading_level =
  3`, `first_only = true`, and `base_url` set to the deployed glossary URL.
- Every alias reviewed against the [vocabulary decisions](../research/2026-11-16-vocabulary-review.md#port-acceptance);
  misleading or retired aliases removed with the reason recorded.
- The exclusions verified in rendered pages: code spans, headings, and text
  already inside a link.
- Not: adding glossary entries, editing definitions for style, or linking terms
  by hand in prose.
- Not: a build-running test in `npm test` or `pytest`; `zensical` is a
  subprocess, and the default suites stay free of one.
- Not: creating `zensical.toml` or `docs/index.md`; P3.1 lands them underneath,
  and this cycle only edits them.

## Configuration

The extension is registered under `project.markdown_extensions` in
`zensical.toml`. Its relevant keys in the installed version are `glossary_file`,
`heading_level` (default 2), `first_only` (default true), `base_url`,
`min_length`, `max_definition`, `case_sensitive` and `labels`.

- `heading_level = 3` matches the `###` entries in `docs/glossary.md`.
- `first_only = true` means one link per page, at the first prose occurrence.
- `base_url` is the published glossary page, `https://satyrn-ai.github.io/satyrn-pi/glossary/`
  under the default directory URLs. It is written out rather than derived, so
  the build does not depend on inference; the check below confirms it agrees
  with `site_url`.
- `min_length` keeps its default. `max_definition` keeps its 280, which truncates
  the longest definitions — Base, Preset, Remedy, Eval suite — into a preview
  ending in an ellipsis. Accepted: the tooltip is a preview and links to the
  full entry. Raising the limit needs evidence a later cycle can produce.
- `case_sensitive` keeps its default of false, so ordinary lowercase prose links
  too — which is why the cycle reads what actually fired rather than trusting
  the setting.

## Alias review

`docs/glossary.md` carries `<!-- zensical-glossary-aliases: ... -->` comments
above its entries. Each alias is read against the vocabulary decisions: one
naming a retired concept, or meaning something ordinary and firing on ordinary
prose, goes. The outcome is durable in the file, since those comments are what
the extension reads; the reasons go in the roadmap row's status cell, or a
research note if the cell would overflow. A pull-request comment survives about
as long as the branch.

A pointer to the review that names the decision it enforces, rather than a second
copy of the reasoning, is what the repository's budget rules ask for.

## Verification, and why it is by hand

The build is a subprocess, so no default test can exercise the extension. The
cycle therefore builds twice and reads the output, recording what it saw.

The success case: add a sentence using a defined term to `docs/index.md`, build,
and confirm the term renders as a link to the glossary at its first occurrence
and not at its second. Revert the sentence or keep it as real content.

The record is every term the extension linked on each page, with the surrounding
phrase. Two pages keep that list readable, and it catches a short ordinary word
firing on prose nobody meant as a term.

The refusal cases, one per exclusion: the same term inside a code span and
inside a heading stays plain text, and a term already wrapped in a link is not
wrapped again. Each has a sibling success case in the same build, so an
unrelated failure cannot satisfy them.

The deployed check repeats the success case at the real URL, because a relative
`base_url` mistake passes locally and fails under the base path. Like P3.2 it
cannot happen inside the pull request: the stack has to reach `main` first, so
the row stays in flight until the deployed page has been read.

The default suite can hold one thing: a file-reading test asserting `base_url`
starts with `site_url`, so a later edit cannot separate them silently.

## Constraints

- Branch `p3.3/glossary-links`, stacked on `p3.2/deploy`.
- `docs/glossary.md` stays the only source; no site variant, no generated copy.
- Spec under 150 lines; no plan, as the work does not branch.
- Documentation lands here: the roadmap row, a changelog line, and any glossary
  entry the alias review changes.

## Decisions

- **Link the first occurrence per page, and stop.** Repeating it reads as an
  advertisement, not a definition. (Assistant.)
- **`base_url` written out and checked, not derived:** an inferred value hides a
  base-path mistake until deployment. (Assistant.)
- **Aliases are reviewed before they are trusted:** they were written for a
  check, not for readers, and some name retired concepts. (Assistant.)
- **Verification by hand, recorded:** the alternative is teaching the default
  suite to run a build, which the rules forbid. (Assistant.)
- **No new entries.** The vocabulary budget is 25 terms and this cycle spends
  none of it. (Assistant.)
- **Truncated tooltips are accepted.** The 280-character default previews most
  entries; the link carries the rest. (Assistant.)
- **The firing list is the check.** Case-insensitive matching is only safe if
  somebody reads what it matched. (Assistant.)

## Left to the builder

- Whether the extension is a table or an inline table in TOML.
- Which aliases go, term by term; the review records the judgement, not a rule.
- Whether the home page's only link per term is the right place for it.

## Verification

- A defined term links once per page, at its first prose occurrence, and points
  at the deployed glossary URL; the fired-term list on both pages has been read,
  and any surprise removed by alias or config rather than by hand-editing prose.
- Code spans, headings and existing links are exempt, each shown beside a
  passing sibling in the same build.
- `uv run zensical build --strict` passes with the extension enabled, the CI
  workflow stays green, and the deployed page repeats the success case.
- The alias review is recorded, and `npm test`, `npm run check:docs` and
  `uv run pytest` still pass.
