# P5.0 Eval CLI: phase 5 design

## Reviewer brief

**Intent:** a contributor can run one command that resolves every input it will
later cite, refuses to start when those inputs are ambiguous, and leaves a record
of what it resolved before any model is asked anything.

**Decisions:** phase 5 splits into P5.1, which resolves and records, and P5.2,
which spawns Pi; P5.1 proves itself with fixtures and starts no child process; the
resolution order is `--worker`, then the installed npm package, then stop; the
server is health-checked before a job directory exists; `runs/` gains `job.json`
and `run.json` only, with `trial.json` arriving in P5.2; Model requests and Elapsed
seconds are counted from records rather than from output; the gate accepts the
declared peer range, but the development target is Pi 1.5.2 and a run on any other
version is not a verified one.

**Non-goals:** spawning Pi, workspaces, prompts, deadlines, settle gates, suites,
graders, verdicts, scores, remedy selection, publishing either package.

**Verification:** the printed resolution matches what `job.json` records; an
ambiguous or missing worker stops before a job directory is created; a failing
health check stops before a job directory is created; `run.json` totals equal the
sum of its trials' records; no default-suite test starts a process or opens a
socket.

## Intent and why

[`docs/domain.md`](../../domain.md) already specifies the target: the resolution
order, the record tree, the boundaries, the statuses and the rule that a partial
record stays inspectable. This cycle implements the first slice of it and nothing
more, because the pieces that follow — a workspace to run in, a Pi child to bound,
a suite to grade — each belong to a different owner and a different review.

The row asked one cycle for the CLI, the records and a demonstration. The
demonstration waits: proving a run needs something to run, and neither the worker
nor the suites exist yet.

## The command

```sh
uvx satyrn-pi eval --suite <name> [--worker <path>] [--base-url <url>]
```

`uvx satyrn-pi eval` runs the published package once it exists; until then the
checkout form is `uvx --from . satyrn-pi eval`. `--base-url` defaults to
`http://127.0.0.1:8001/v1`, and `--suite` must resolve to a fixture suite in P5.1.

## Resolution, in order

1. **Worker.** `--worker <path>` wins; else the installed npm package is looked
   up. If neither resolves, or both would and disagree, the run stops. Proved with
   a fixture worker directory and an injected lookup, because the npm package has
   no worker until P8.
2. **Pi.** The binary on `PATH`, and its version against `peerDependencies` —
   `^1.1.0`, which is what the package promises an installer. The port's target is
   **1.5.2**: that is what development, the eval guide and P5.2's spawned child are
   verified against. A run on another version inside the range is legal and
   unverified, and `job.json` records the version so the difference is visible
   rather than assumed. This machine reported 1.1.0, the floor, and development
   moves to 1.5.2. `latest` is now 1.6.0, which the range also admits: an
   installer can get a version no cycle here has run. Narrowing the range belongs
   to a release cycle; until then the record names the gap.
3. **Suite.** A fixture suite and its version, from package data.
4. **Server.** A health check against the origin of `--base-url`.

Resolution prints one line per input, and then `job.json` becomes the citable
copy of the same facts.

## Preflight, and what a failure leaves behind

The health check runs **before** the job directory is created, so a failure leaves
no half-made run: it prints what failed and exits non-zero. An empty directory is a
worse signal than an error — the same holds for an ambiguous worker and for a Pi
version outside the range.

## Records

```text
runs/<date>-<suite>/<job>/
  job.json    what was resolved and asked for
  run.json    the job summary, written last
```

`job.json` carries the suite and its version, CLI version, repetition count, any
preregistered rule, worker path and version, Pi version, model, base URL and the
start time; `run.json` the status, aggregated counts and exit status. Directories
are `<YYYY-MM-DDTHHMMSSZ>-<six hex>`, so concurrent runs cannot collide, and
`runs/` stays ignored.

## Counting

- **Model requests** counts what the model received, summed from trials. In P5.1
  the trials are fixtures: the rule lands, not a measured number.
- **Elapsed seconds** is wall-clock from the job's start to `run.json`, per job and
  per trial, and is never presented as a sum: adding trial clocks double-counts
  time the job was not running.
- Only Model requests aggregates, and no aggregate is written without the trials it
  sums.

A run is the CLI invocation; a session is a child-process chain inside a trial.
P5.1 has no session, so no field claims one.

## The split

| Cycle | Ships | Leaves |
| --- | --- | --- |
| **P5.1** | The entry point, resolution and its printed form, preflight, `job.json`, `run.json`, the counting rules and the exit contract, proven with fixtures. | Any child process; a real suite; a verdict. |
| **P5.2** | Workspace preparation, the Pi child in print mode with closed stdin and a private agent directory, the process-group deadline, `trial.json` at each boundary, and one trial end to end against a stub task. | Grading, which P6.1 owns; remedies, which their cycles own. |

## Decisions

- **Split phase 5; P5.1 resolves and records.** (Paul, this phase's brainstorm.)
- **Fixtures, not a spawned Pi.** The default suite must stay subprocess- and
  socket-free, so real execution needs its own deliberate path in P5.2.
  (Assistant.)
- **Preflight before the job directory.** A failed start leaves an error, not a
  half-made record. (Assistant.)
- **The gate accepts the peer range; the target is 1.5.2.** The range is the
  installer's promise, the target is what we verify against, and `job.json`
  records which one ran so the two never get conflated. (Assistant, on Paul's
  instruction to stay with the target.)
- **`satyrn-pi` is the console script name**, matching both registry names.
  (Assistant.)
- **Job identifiers carry a timestamp and a random suffix.** (Assistant.)

## Left to the builder

- The Python module layout under `src/satyrn_pi/`, and whether the CLI is a module
  or a package with submodules.
- How fixtures represent a suite and a worker: directory shape, and whether the
  worker fixture is a stub extension or only a manifest.
- How the health probe and the package lookup are injected so tests need no socket
  and no install.
- The exact field names in `job.json` and `run.json`, within the facts listed above.
- The eval guide's location and whether it publishes.

## Verification

- Printed resolution and `job.json` agree field for field; a mismatched pair fails
  a test.
- A missing worker, an ambiguous worker, an out-of-range Pi version and an
  unreachable server each stop before a job directory exists, each shown failing.
- `run.json`'s Model requests equals the sum of its trials, tested against
  fixtures whose total differs from every individual record; Elapsed seconds is
  the job's own clock and a test fails if it is written as a sum.
- `npm test`, `uv run pytest` and `npm run check:docs` pass; the default-test
  tripwire is unchanged and still catches a planted socket or child process.
- `pi --version` reports 1.5.2 on the development machine, and a version outside
  the declared range stops the run before a job directory exists.
