# P3.2 continuous integration and deployment: design

## Reviewer brief

**Intent:** a pull request that breaks the site or a default suite cannot merge,
and `main` publishes the site to a URL that has been opened and checked.

**Decisions:** one workflow file; pull requests and `main` install with `npm ci`
and `uv sync --locked`, run both default suites and
`uv run zensical build --strict --clean`; a deploy job gated to `main` with the
`github-pages` environment; Pages set to publish from Actions by someone with
admin; the URL recorded in the roadmap and `README.md` and verified by hand.

**Non-goals:** new content, glossary configuration, a custom domain, caching
the site output, marked integration tests, a release or package publish.

**Verification:** a pull-request run passes; a deliberately broken link fails the
same job; after merge, the first `main` deploy is green and its URL loads in
light and dark with the glossary reachable; `site_url` matches the recorded URL.

## Intent and why

This is the repository's first workflow. Nothing today runs the default suites
on a pull request, so the gates P2.3–P2.5 re-earned are enforced only by whoever
remembers to run them. The same file is what makes deployment real, and a real
base path is what P3.3 needs before its glossary links can be checked.

## Goals and non-goals

- One workflow that gates every pull request on the default suites and a strict
  site build, and deploys `main` to GitHub Pages.
- Pages configured to publish from Actions, and the resulting URL recorded in
  the roadmap row and `README.md`, with `site_url` in `zensical.toml` matching.
- The deployed site opened and checked by hand in light and dark.
- Not: the site's content, theme or glossary configuration, which P3.1 and P3.3
  own.
- Not: a custom domain, a release, a package publish, or any caching of the site
  output — Zensical's documentation says caching is not recommended while its
  behaviour is revised.
- Not: marked integration tests. They exist to be run deliberately, not in CI.

## The workflow

One file, `.github/workflows/site.yml`, with two jobs.

- **Build**, on `pull_request` and on pushes to `main`: checkout; Node from
  `package.json`'s engines floor; `npm ci`; `astral-sh/setup-uv`; `uv sync
  --locked`; `npm test`; `uv run pytest`; `uv run zensical build --strict
  --clean`; upload `site` as the Pages artifact.
- **Deploy**, `needs` the build, `if` the ref is `main`, with
  `permissions: pages: write, id-token: write`, the `github-pages` environment,
  a concurrency group that cancels superseded deployments, and
  `actions/deploy-pages`. The job's URL output is the value that gets recorded.

Both jobs are explicit about versions rather than tracking `latest`: the lock
file and the Node floor are the repository's declared inputs, and a workflow
that quietly upgrades them is a measurement the repository did not ask for.

## Recording and verifying the URL

`site_url` becomes `https://satyrn-ai.github.io/satyrn-pi/`, trailing slash
included — Zensical concatenates paths onto it. The same URL goes into the P3.2
roadmap row and `README.md`, marked as the deployed site rather than an install
target.

That line records the configured address, which the repository determines
before any deploy. It is not a claim that a page renders. The claim is the
verification, and it cannot happen inside the pull request: the workflow has to
reach `main` before Pages will build and publish. So the order is: merge; the
first `main` deploy runs; open the root, open the glossary, follow a link
between them, check light and dark at the deployed path rather than `/`; record
the run; then the row closes. Until that run is green the row stays in flight,
and a failed first deploy reopens the cycle rather than closing it.

## Dependencies

- Someone with repository admin sets Settings → Pages → Source to GitHub
  Actions before the first deploy. Without it the deploy job fails, so the
  setting is a named prerequisite in the pull request, not a surprise.
- Record what the `github-pages` environment actually requires — reviewers,
  wait timer, or nothing. If a deploy waits for approval, "merge publishes" is
  false and the verification follows the approval, not the merge.
- Requiring the build check on `main` is an admin policy change affecting every
  pull request. This cycle supplies the check; asking for it is a separate
  decision, and the stack merges into `p3.1/site-identity` rather than `main` in
  any case.

## Constraints

- Branch `p3.2/deploy`, stacked on `p3.1/site-identity`.
- The default suites stay model-, network- and subprocess-free on a developer's
  machine. Running them in CI with a network is not a contradiction: the rule
  governs what the tests do, not where they run.
- `--clean` on every build, so a deleted page cannot survive in `site/`.
- Spec under 150 lines; no plan, as the work does not branch.
- Documentation lands here: the roadmap row's status, the URL in `README.md`,
  and a changelog line.

## Decisions

- **One workflow, two jobs, not two workflows.** The build is the gate and the
  deploy is a consequence; splitting them lets the gate and the artefact drift.
  (Assistant.)
- **The workflow runs both default suites.** The first CI file in the repository
  should gate the repository, not only the site it happens to be named after.
  (Assistant; this widens the P3.2 row.)
- **Strict in the command, not only in the config.** `--strict` is passed
  explicitly so the workflow's contract is readable in one place, and
  `strict = true` stays in `zensical.toml` so local builds match. (Assistant.)
- **No caching of the site build.** Zensical's own guidance says not to while
  its caching is being revised. (Assistant.)
- **The URL is verified by hand once and recorded.** A green deploy proves the
  upload, not that the base path works. (Assistant.)
- **Verification happens after merge, and the row waits for it.** The workflow
  cannot deploy from a pull request, so the cycle's evidence includes a `main`
  run; closing before that would claim a site nobody opened. (Assistant.)
- **Admin actions are prerequisites, not part of the change.** Pages and branch
  protection belong to whoever administers the repository; the cycle does not
  assume either has happened, and it records which did. (Assistant.)

## Left to the builder

- Exact action versions, the concurrency group's key, and whether the deploy
  job needs its own checkout.
- Whether the build job sets a timeout.
- How the prerequisite and the verified URL are recorded in the pull request.
- Whether `README.md` gains a short "the site" section or a single line.

## Verification

- The workflow passes on the pull request, and the log shows both suites and the
  strict build running.
- Replacing a link target with a missing anchor fails the build job; reverting it
  passes, proving `--strict` is load-bearing rather than decorative.
- After merge, the first `main` deploy is green; the root and glossary load at
  the recorded URL, both pages link to each other, and light and dark render.
- `site_url`, the roadmap row and `README.md` agree on one URL, and the row's
  status quotes the run that verified it.
