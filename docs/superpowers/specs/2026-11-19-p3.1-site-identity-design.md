# P3.1 site identity: design

## Reviewer brief

**Intent:** a visitor who reaches the project URL sees a page that looks like a
Satyrn project and can open the glossary from it.

**Decisions:** a minimal root `zensical.toml`; the Satyrn stylesheet and chrome
from `7508bd7` with one font face and a licence notice; the published set exactly
`index.md` and `glossary.md`, asserted by a file-reading check and confirmed once
against the built output; the glossary stays the single source, its one outbound
link absolute; no install line for an unpublished package; no CI, no
auto-linking.

**Non-goals:** Actions, Pages, `zensical_glossary`, aliases, guides, the source
site's blog, hero, feed and landing config, a shared theme package.

**Verification:** `uv run zensical build --strict` and `serve` locally; the built
output listed against the two pages plus named fixed files; the check fails on a
planted page; light and dark both render; `npm test`, `uv run pytest` and the
weight check pass.

## Intent and why

The project URL is the first thing a stranger sees, and the npm package is not
published yet, so the site's first job is identity rather than instruction. The
[acceptance rules](../../rules-applicability.md#documentation-site-acceptance)
describe the whole site; this cycle needs neither a deployment nor a second
consumer for the glossary extension. P3.2 deploys because links need a base
path, and P3.3 links because its links need that path.

## Goals and non-goals

- A root `zensical.toml` carrying only what this cycle needs.
- The Satyrn stylesheet and the overrides that draw the header, footer, logo and
  nav, adopted from `7508bd7` with the revision, files and edits recorded.
- A home page at `docs/index.md`, with the published set limited to it and the
  glossary, and a check that fails when a third page would be published.
- `uv run zensical serve`, checked in light and dark.
- Not: the Actions workflow, Pages, `site_url` or the public URL (P3.2); the
  glossary extension, tooltips, first-occurrence links or aliases (P3.3).
- Not: any installer or contributor guide (the first is P4.1); the source site's
  blog, hero, feed, carousel, authors, tags, landing sections or
  `zensical.toml`; a shared theme package across Satyrn repositories.
- Not: an accessibility page. The source footer links one, and inventing a page
  to satisfy a link is worse than the missing link.
- Never: publishing `docs/sdd.md`, `docs/superpowers/**` or
  `docs/provenance/**` because a new document arrived and nothing noticed; a
  second glossary copy; a pruned stylesheet fork; an install line for an
  unpublished package; a URL claimed before P3.2.

## Layout and configuration

- `zensical.toml` at the repository root, written rather than copied: `strict`,
  `docs_dir`, `site_dir`, theme features, palette, two `nav` entries,
  `extra_css`, `custom_dir`, `copyright`, `exclude_docs`. `docs_dir = "docs"`
  keeps the glossary's only copy; `site_dir` is ignored by git and by the
  weight check.
- No menubar: the source's is built from `extra.nav_menu` and would render empty
  with two pages, so the sidebar carries both entries.
- The locked Zensical stays locked; if the chrome diverges, the overrides adapt
  and the divergence is recorded, not the lock.

## Theme assets

- `satyrn.css` at `7508bd7` (78,299 bytes) is adopted whole so the family look
  is the source's; only the outline and script `@font-face` blocks go.
- Ship only `triplecharm-sans-webfont.woff2` (51 kB of six files' 464 kB): sans
  is the only face rendered, all six break the weight budget, and the `.woff`
  fallback goes too.
- The face is a purchased Creative Market webfont capped at 10,000 page views a
  month; a notice beside it records vendor, purchase date, licence and cap,
  which the source keeps only in a CSS comment.
- Body copy and code use Zensical's own stack: the source fetches Lora and
  JetBrains Mono from Google Fonts, and this site makes no external request.
- Adopt only overrides the chrome needs; blog, hero, carousel, author, tag and
  feed material stays behind.

## Publishing exactly two pages

`tests/published-pages.test.mjs` reads `docs/**/*.md` and the configured
exclusions and asserts the set is exactly `index.md` and `glossary.md`. Shown to
fail first: add a page, watch it fail, exclude it. It reads files only, so it
belongs in the default suite; the build itself stays out, being a subprocess.

The check is the only guard: a planted third page builds strictly and publishes
without complaint. The cycle therefore builds once by hand, lists
`site/**/*.html`, and records it in the pull request — two pages plus
`404.html`, `sitemap.xml`, the search index and copied assets.

## The published pages

`docs/index.md` follows the source learning centre's shape — what it is, who it
is for, where to go — and takes no prose from it. It names the project, says
plainly that this is a small local model used as a bounded coding worker inside
Pi, says the port is in progress, and links to the repository and the glossary.

It carries no install command, since neither package is published; that line
arrives with the cycle that verifies the artefact. It carries no rate, score or
run claim, and stands on its own rather than deriving from the README. The
glossary's budget line and alias comments stay: one source, not a site variant.
`docs/glossary.md`'s single outbound link, `domain.md`, becomes an absolute
repository URL, so the page builds strictly with no link leaving the site — the
only content edit here, and the one the P3.1 row allows.

## Constraints

- Branch `p3.1/site-identity`, stacked on `p3.0/phase-3-cycles`.
- Default suites stay model-, network- and subprocess-free. There is no plan to
  write, as no work branches. Weight budget is 200 files and 1,000,000 bytes;
  the tree is at 71 files and 495,449 bytes, and these assets add ~130 kB.
- Documentation lands in this pull request: the roadmap row, a changelog line
  under `[Unreleased]`, and glossary entries for anything new.

## Decisions

- **Minimal config over an adapted copy; stylesheet whole, one face.** Adopt
  assets, write configuration; weight forces the single font.
- **Only two pages, enforced by a check.** A decision, not a default. (Paul.)
- **The font ships with a notice.** It is already public in the source
  repository and the display face is most of the family look. (Paul.)
- **Copyright only in the footer** — `© 2026 Satyrn AI`, no accessibility link,
  no social row — with that page deferred to a backlog entry. (Paul.)
- **No external font request,** so body copy differs from satyrn.ai here.
- **No menubar, and the lock stays.** Two pages do not fill a menubar, and
  P1.1's lock is not this cycle's to change.
- **Home page and README stand separately:** product-facing and contributor
  setup, overlapping deliberately and needing no check.
- **Glossary link becomes absolute.** One source and a strict build, at the cost
  of a GitHub URL on a public page; the `default`/`slate` palette comes from the
  source so light and dark behave as satyrn.ai does.

## Left to the builder

- Which override files the chrome requires, their edits, the `exclude_docs`
  syntax for the installed version, and the check's file and test names.
- Where the stylesheet, font and notice live under `docs/`.
- The home-page prose within these constraints (Ben reviews it) and the notice's
  wording.

## Verification

- `uv run zensical build --strict` succeeds and `serve` shows both pages in the
  Satyrn chrome, light and dark; the built output matches the two pages plus the
  named fixed files.
- The check fails on a planted third page and passes on the tree; `npm test`,
  `npm run check:docs` and `uv run pytest` pass; the weight check is inside
  budget; the roadmap row names the adopted revision and assets, and the
  changelog has its line.
